1. Executive Summary

The Omega Trading Company is a fully automated algorithmic trading bot designed for Indian index options markets. It trades NIFTY 50, Bank NIFTY, and SENSEX options on the NSE and BSE exchanges through the Dhan broker API. The system operates on a 5-factor confluence model where all five independent technical indicators must agree before any trade is taken.

The system supports both BUY mode (buying options when ADX signals a trending market) and SELL mode (selling options when ADX signals a ranging market). Every trade passes through a 9-gate risk engine and 15-scenario pre-trade guardrail framework before execution. Position management employs a 4-level dynamic SL/TP escalation system with ATR-based trailing stops after the final level is breached.

3. Signal Processing Pipeline

Every signal traverses a strict 12-step pipeline. If any step rejects the signal, the trade is blocked and the reason is logged. This pipeline is the core entry logic in strategies/omega_complete.py lines 160-536.

Step 1: Signal Reception

TradingView fires a JSON webhook to the FastAPI server at /webhook. The payload includes: symbol, side (BUY_CE, BUY_PE, SELL_CE, SELL_PE, EXIT), confidence (HIGH/MEDIUM/LOW), score (0-100), strike, sl, atr, and various indicator values (ADX, RSI, volume ratio, SuperTrend direction, VWAP position, Bollinger squeeze state).

Step 2: Exit Signal Check

If side == "EXIT", the system routes directly to _handle_exit() which has 4 protective checks before closing any position: minimum 10-minute hold time, skip if at dynamic level 2+ (let levels manage), skip if currently in profit (let trailing stop manage), and skip if unrealized loss is under Rs 200 (let SL handle minor fluctuations).

Step 3: Opening Range Filter

All signals before 09:20 IST are blocked. Rationale: the first 5 minutes after market open (09:15) are extremely choppy with gap reactions and auction noise. This filter prevents whipsaw entries during the opening volatility.

Step 4: Theta Filters (SELL-specific)

  • SELL entry before 11:30 IST: Blocked. Theta decay (time value erosion) is too slow in the morning for option selling to be profitable on an intraday basis.
  • SELL entry after 12:30 IST: +5 score bonus. Theta decay accelerates in the afternoon, making option selling more favorable.
  • BUY entry after 14:30 IST: -10 score penalty. Rapid time decay in the last hour erodes option premium, making buying options risky.

Step 5: CE Bias Boost

All CE (Call) trades get +3 score. Historical data shows CE trades outperform PE (Put) trades in Indian markets due to the natural long bias of equity indices.

Step 6: Loss Recovery Mode

After 2+ consecutive losses: 15-minute cooldown, only MEDIUM/HIGH confidence accepted, minimum score raised to 55. After 4+ losses: minimum score raised to 60, quantity reduced to 1/3, SL tightened by 2%. The BANKNIFTY symbol also gets +10 added to minimum score requirement as a historically net-losing instrument.

Step 7: Instrument Resolution & Option Chain

The webhook symbol is resolved to an instrument name (NIFTY, BANKNIFTY, SENSEX). If the option chain resolver is available (live feed active), it picks the ATM option contract with the best liquidity from Dhan's option chain API. Otherwise, it computes the ATM strike from the underlying LTP.

Step 8: Correlated Position Guard

Same-index duplicate positions are blocked (e.g., cannot have two LONG NIFTY positions simultaneously). Maximum 2 correlated index positions in the same direction across all indices.

Step 9: Guardrail Checks

Per-trade risk check ensures the trade risk (entry - SL) * quantity does not exceed 5% of capital (Rs 10,000 on Rs 2L capital in paper mode). Sector allocation check ensures total NSE exposure stays below 70% of capital.

Step 10: Trade Memory Evaluation

If enough historical data exists (5+ trades for the symbol), the memory system provides: Kelly criterion position sizing (half-Kelly), pattern-based blocking (e.g., 5+ consecutive losses on a symbol triggers a 7-day ban), score adjustments from learned rules (+/- based on statistical significance), and position size modifiers from drawdown protection.

Step 11: Position Sizing

Four sizing mechanisms stack multiplicatively: (a) Volatility regime sizing (HIGH_VOL: 0.5x, CHOPPY: 0.7x, TRENDING: 1.2x), (b) ATR-based risk sizing (limits risk to 1-3% of capital based on ATR distance), (c) Loss recovery sizing (halved after 3 losses, 1/3 after 4), (d) PE size reduction (PEs get 80% of normal quantity due to historical underperformance).

Step 12: Order Placement

The Order Manager places a LIMIT order with 0.5% slippage buffer on Dhan. If the fill is confirmed, a Position is created with dynamic SL/TP levels, a broker SL-LIMIT order is placed, margin is deducted from the wallet, and an iMessage/Telegram alert is sent with fill details.

The script analyses market state to determine BUY vs SELL mode:

  • BUY mode (ADX > 25): Market is trending. Buy ATM options to profit from directional moves.
  • SELL mode (ADX < 20): Market is ranging/choppy. Sell OTM options to collect premium as theta decays.
  • No-trade zone (20 ≤ ADX ≤ 25): Ambiguous regime. No signals generated.

4.4 Signal Scoring (15 Factors)

Each signal receives a score from 0 to 100 based on 15 weighted factors. The score determines the confidence tier:

  • HIGH confidence (score ≥ 72): Strong confluence, wider SL/TP allowed, full position size
  • MEDIUM confidence (55 ≤ score < 72): Moderate confluence, standard SL/TP
  • LOW confidence (score < 55): Weak confluence, tighter SL/TP, may be filtered out

Minimum score for entry is 45 in paper mode, 55 in live mode. Additional score gates apply after consecutive losses.

6.1 Gate Details

Gate 2: Daily Loss Limit (Rs 3,000)

Why Rs 3,000? On Rs 1,00,000 capital, a 3% loss requires only 3.09% recovery to break even. A 5% loss requires 5.26% recovery — the recovery curve gets exponentially harder. Rs 3,000 keeps the bot within the recoverable zone. When breached, the _bot_killed flag is set and persists until reset_daily() is called the next trading day.

Gate 5b: Progressive Loss Reduction

When daily P&L reaches -50% of the max daily loss limit (i.e., -Rs 1,500), the system reduces max concurrent positions from 2 to 1. This prevents a cascading loss scenario where two losing positions compound the damage. The system must recover to above -50% before the second slot reopens.

Gate 6: SL Cap (Confluence-Scaled)

The stop-loss distance is capped as a percentage of entry price. High-confidence trades (score ≥ 75) get a tighter 8% cap because the signal is stronger, while lower-confidence trades get a 10% cap. This prevents outsized losses on any single trade regardless of ATR-based sizing.

7. Dynamic SL/TP Level Escalation

Instead of a fixed stop-loss and take-profit, the system uses a 4-level escalation model. When price hits the take-profit of Level N, the SL moves up to the previous TP and a new, wider TP is set for Level N+1. This locks in profit while letting winners run.

7.3 Level-Up Mechanics

When price hits the current TP:

  1. The old TP becomes the new SL (profit locked at this level).
  2. A new, wider TP is set from the level table.
  3. dynamic_level increments.
  4. The broker SL order is cancelled and replaced at the new SL price.
  5. If price has already blown past multiple levels (e.g., a gap move), the system performs a multi-level jump — it iterates through all applicable levels in one pass.
  6. After L4 is breached, the system enters ATR Trail Mode — no more levels, just a 1.5x ATR trailing stop from the peak price.

8. Trailing Stop & 5-Layer Profit Engine

The monitor_positions() method runs every 1 second and implements a 5-layer profit management system. This is the most complex part of the codebase at 250 lines.

8.1 Layer 1: Breakeven Lockdown

At 3% profit, the stop-loss moves to entry price + 0.1% (just above breakeven). This ensures that once a trade is 3% in profit, it can never turn into a loss. The breakeven_locked flag is set permanently for the position.

8.2 Layer 2: Scale-Out in 3 Tranches

Partial exits lock in profit while letting the remainder ride:

TrancheTrigger (HIGH/MEDIUM/LOW)Exit QuantityRemaining
15.0% / 4.0% / 3.5% profit1/3 of position2/3
29.0% / 7.0% / 5.5% profit1/2 of remaining1/3 of original
3—Full exit via SL or TP0

8.3 Layer 3: Time-Decay Targets (Theta Awareness)

Options lose value over time. The system progressively reduces TP targets based on hold duration:

  • 60-120 minutes: TP reduced to 75% of original distance from entry
  • 120+ minutes: TP reduced to 50% of original distance from entry
  • Safety floor: Decayed TP must stay at least 0.5x ATR above the active SL

8.4 Layer 4: Momentum Hold

When price hits the TP and the system is in ATR trail mode (past all 4 levels): if profit is within 0.3% of peak profit AND hold time is under 2 hours, the TP exit is delayed. This lets strongly trending trades continue to run instead of exiting at a potentially intermediate high.

8.5 Layer 5: ATR-Based Trailing Stop (evaluate_trail)

The core trailing algorithm in risk_engine.py uses time-aware phased progression:

Time PhaseTrail WidthRationale
< 10 minutes3.0x ATRLet trade develop, avoid premature exits
10-30 minutes2.5x ATRMedium room as direction establishes
30-60 minutes2.0x ATRTighter as move matures
60+ minutes1.5x ATRTight — theta eating, lock profits

Profit-phase overrides:

  • < 1.0x ATR profit: No trail tightening (trade hasn't moved enough)
  • 1.5x ATR profit: SL moves to breakeven
  • 3.0x ATR profit: Time-based trail from peak
  • 5.0x+ ATR profit: Override to tight 1.5x ATR regardless of time

8.6 SL Grace Period

When an SL is hit, there is a 90-second grace period (SL_GRACE_SECONDS = 90). If the position has been held for less than 90 seconds, the SL hit is ignored. This prevents premature exits on opening-bar volatility where price momentarily touches the SL and then reverses.

8.7 SL-Skip Freefall Detection

If LTP falls MORE than 0.5% past the SL (i.e., the SL was "skipped" by a gap move or latency), the system triggers an emergency market exit. This protects against scenarios where the SL limit order didn't get filled due to fast price movement.

9. Trade Memory & Statistical Learning

File: core/trade_memory.py — 990 lines. The trade memory is a self-learning system that records every trade outcome and discovers statistically significant patterns. These patterns then influence future trading decisions.

9.1 Architecture

The memory system stores three types of data in a single JSON file (data/omega_memory.json):

  • Trades: Complete record of every trade with 25+ fields (entry/exit times, prices, indicators, outcome, R-multiple, etc.)
  • Lessons: User-taught rules (e.g., "Don't trade BANKNIFTY on Wednesdays")
  • Adaptive Rules: Machine-discovered patterns from statistical analysis

9.2 Pattern Detection

The analyze_patterns() method runs after every 10 trades and groups trades by 9 dimensions:

  • Entry hour (0-23)
  • Entry day of week (Mon-Fri)
  • Symbol base (NIFTY, BANKNIFTY, SENSEX)
  • ADX zone (flat, weak, moderate, strong, very_strong)
  • Signal confidence (HIGH, MEDIUM, LOW)
  • SuperTrend direction
  • VWAP position (above/below)
  • Volatility regime (NORMAL, HIGH_VOL, CHOPPY, TRENDING)
  • Exit reason (TRAIL_SL, SIGNAL_EXIT, SQUARE_OFF, etc.)

9.3 Statistical Significance Testing

For each group, a two-proportion z-test (at 90% confidence, z ≥ 1.65) compares the group's weighted win rate against the overall baseline win rate. If the difference is statistically significant, a rule is created:

  • Group wins less than baseline: PENALIZE action, negative score modifier (up to -30)
  • Group wins more than baseline: BOOST action, positive score modifier (up to +25)
  • 5+ consecutive losses on a symbol: BLOCK action, 7-day ban on that symbol
  • SL-skip rate above 10%: REDUCE_SIZE action, position size halved

9.4 Decay & Pruning

  • 30-day half-life: Older trades contribute less weight via exponential decay: weight = e^(-0.693 * age / 30)
  • 7-day ban expiry: Symbol bans automatically lift after 7 days
  • 90-day rule max age: Rules with fewer than 3 hits in 90 days are pruned as stale
  • 45% effectiveness threshold: Rules that predict correctly less than 45% of the time (after 15+ evaluations) are deactivated

9.5 Multi-Factor Combinations

Beyond single-dimension analysis, the system also tests combinations like "NIFTY at 10:00" or "SuperTrend bullish in strong ADX zone." These catch nuanced patterns that single factors miss.

9.6 Health Monitoring

The memory system generates health reports with status levels: HEALTHY, DEGRADED (7-day win rate < 40%), CRITICAL (win rate < 30% or 5+ consecutive losses). Degraded/Critical status triggers alerts via iMessage/Telegram and recommends raising the minimum score threshold.

11. Order Management & Execution

File: core/order_manager.py — 337 lines. The Order Manager handles idempotent order placement with retry logic and ghost fill detection.

11.1 Key Features

  • Idempotency: Every signal has a unique tag. Duplicate signals are silently ignored via exists(tag) check.
  • Limit Orders Only: The system NEVER places market orders. All entries use LIMIT orders with a 0.5% slippage buffer above LTP (for buys) or below LTP (for sells). This prevents fill at extreme prices during volatility.
  • Exponential Backoff Retry: On broker errors, the system retries up to 4 times with exponential backoff (1s, 2s, 4s, 8s). Rate limit errors (DH-904) are handled separately with appropriate wait times.
  • Auth Failure Handling: On DH-901 (auth expired), the system sends a CRITICAL alert via iMessage/Telegram instructing manual intervention. No retry is attempted — the token must be manually renewed at api.dhan.co.

11.2 Ghost Fill Detection

After all retries are exhausted, the system checks for "ghost fills" — situations where the order actually went through on the broker side but the confirmation response was lost due to a timeout. It queries broker positions for the security and, if a position exists, creates a synthetic OrderResponse with the broker's fill price. This prevents the system from thinking a trade failed when it actually succeeded.

11.3 SL Order Management

After each entry, a broker-side SL-LIMIT order is placed with a 2% buffer. This means the SL trigger price and the actual limit price differ by 2%: for a LONG position, the limit is 2% below the trigger to ensure fill. As trailing stops move, the old SL order is cancelled and a new one placed at the updated price.

18.6 Integration with Strategy Engine

The ML engine hooks into OmegaStrategy.process_signal() as a pre-trade gate (between guardrails check and trade memory check). On each signal:

  1. Extracts 44 features from the live candle buffer
  2. Regime detector classifies market state → adjusts SL/TP multipliers and volatility regime
  3. Signal classifier predicts WIN/LOSS probability
  4. If confidence < 55% or model predicts loss with > 65% confidence → signal blocked
  5. If regime is CHOPPY and signal score < 65 → signal blocked

On trade exit, the outcome (win/loss, P&L, features at entry) is recorded to the trade buffer. After 20 new trades, both models auto-retrain on the accumulated data.

18.7 Validation Framework

Walk-Forward Validation

Trains on a sliding window (default 50 samples), tests on the next 10. Measures accuracy, precision, recall, and F1 per window. Prevents overfitting by mimicking how the model would be retrained in production.

Feature Importance

Permutation-based: for each of the 44 features, shuffles that column N times, measures accuracy drop. Features with larger drops are more important for prediction. Used to prune noisy features and understand what drives predictions.

21. Known Limitations & Assumptions

  1. Backtest Accuracy: The backtester uses underlying index price as a proxy for option premium movement. In reality, IV expansion/crush, theta decay, and gamma curvature significantly affect option premiums. The backtest overestimates P&L for far OTM strikes and underestimates for ATM.
  2. Single Broker: Only Dhan is currently supported. There is a broker_base.py abstract interface but no Zerodha, Angel, or other broker adapters have been built.
  3. No Real Historical Option Data: The system cannot backtest with actual option premium tick data. This would require purchasing data from NSE or using a paid provider.
  4. No Greeks Calculation: The system does not compute or use IV, delta, theta, gamma, or vega for decision-making. Option selling is done purely on directional signals + ADX regime, not on volatility surface analysis.
  5. Single Timeframe: Only 5-minute candles are used. No multi-timeframe analysis (e.g., daily trend + 5-min entry) is implemented.
  6. No Market Depth (Level 2): The system trades on LTP alone without considering order book depth, bid-ask spread, or liquidity profile.
  7. Yahoo Finance Dependency: The Python signal generator depends on Yahoo Finance for candle data, which is free but unreliable and delayed. The TradingView webhook path bypasses this but requires a paid TradingView subscription.
  8. No Slippage Model: The 0.5% slippage buffer is applied but no actual slippage tracking or modeling is done.
  9. No Overnight Positions: The system is strictly intraday with forced square-off at 15:10 IST. Positional or swing trades are not supported.
  10. VPS Single Point of Failure: If the Oracle Cloud VPS goes down, all monitoring stops. There is no failover or redundant instance.

22. Open Questions for Contributors

These are design questions, feature ideas, and architectural decisions that remain open. Each one is an opportunity for a contributor to add value to the system. They are ranked roughly by impact.

Q1: How should the system incorporate Greeks (IV, Delta, Theta)?

Currently, option selling decisions are based purely on ADX regime (ranging = sell). Should the system require IV percentile > X before selling? Should delta be used to select strike prices (e.g., sell 0.15-delta OTM)? How would this affect the signal scoring model?

Q2: Should the backtest use actual option premium data?

The current proxy-based approach (underlying price change = option premium change) is known to be inaccurate. Would purchasing historical option tick data from NSE or a data vendor be worth the cost? How would the backtest engine need to change?

Q3: Is 0-DTE (same-day expiry) trading worth the risk?

The guardrails block new 0-DTE entries after 12:30. But 0-DTE options have the fastest theta decay, which benefits option sellers. Should there be a separate 0-DTE strategy with tighter risk parameters?

Q4: How should the system handle gap openings?

If the market gaps up/down significantly at open, the SL from the previous candle may already be breached. Should the system have gap-specific logic (wider initial SL on gap days, reduced size, or a gap-and-reverse detection)?

Q5: Should multi-timeframe analysis be added?

Currently, only 5-minute candles drive signals. Adding a higher timeframe filter (e.g., "only BUY_CE if the 1-hour trend is also bullish") could reduce false signals. How should the timeframe hierarchy be structured?

Q6: Is the 30-day half-life correct for trade memory decay?

The trade memory system uses a 30-day half-life for exponential decay. Is this too short (loses valid patterns too fast) or too long (keeps outdated patterns active)? Should the half-life vary by market regime?

Q7: How should the system handle broker API token expiration?

Dhan tokens expire daily. The current system sends an alert and stops trading. Should the system attempt auto-renewal? Should there be a watchdog that pre-checks token validity before market open?

Q8: Should there be a maximum position hold time?

Currently, positions are held until SL, TP, or square-off. Should there be a maximum hold time (e.g., 2 hours) after which positions are exited regardless of P&L? Options theta decay accelerates over time.

Q9: How should the system handle multiple simultaneous signals?

If NIFTY BUY_CE and BANKNIFTY BUY_CE arrive within seconds, the current system processes them sequentially. Should there be a queue with priority scoring? Should the system prefer one index over another?

Q10: Is the current alerting sufficient?

The system uses iMessage and Telegram for alerts. Should there be an escalation matrix (e.g., phone call for CRITICAL errors)? Should alerts include more context (current P&L, open positions, risk utilization)?

Q11: Should the system support multiple strategies?

Currently, only "omega_complete" strategy exists. Should the architecture support running multiple strategies simultaneously (e.g., a momentum strategy + a mean-reversion strategy)? How would risk be shared between strategies?

Q12: How should the system handle exchange maintenance/holidays?

NSE/BSE have scheduled maintenance windows and public holidays. Should the system have a holiday calendar that prevents the bot from starting on non-trading days? Should it handle early market closures (like Muhurat trading)?

Q13: Should there be an A/B testing framework?

To compare parameter changes (e.g., different SL percentages or trailing widths), an A/B testing framework could split signals between two parameter sets and compare outcomes. How should this be implemented without doubling capital requirements?

Q14: Is the Kelly criterion sizing too aggressive or too conservative?

The system uses half-Kelly with a 25% cap. Academic literature suggests even quarter-Kelly for options. Should the fractional Kelly be reduced? Should it vary by instrument volatility?

Q15: Should the system have a "warm-up" period each day?

Currently, the system starts accepting signals at 09:16. Should there be a period where it observes market behavior (e.g., first 30 minutes) and adjusts parameters (SL width, position size) based on opening volatility before taking any trades?
